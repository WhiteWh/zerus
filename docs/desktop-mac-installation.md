# Dormant Mac installation selection

G1's optional `macos-native-peer` installation module selects both expectations
from the current process's own verified signed paired bundle. It has no caller,
listener, worker, launch, signing, installer or registration path. A selection
and its observations are passive data, with no current producer, profile,
configuration, challenge, lease, bootstrap or native-effect authority.

Genuine running-self positive: **not qualified; requires .25.2 genuine paired
signing**. The separate positive subgate remains open. Native bare/unsigned
refusals and synthetic metadata/file-generation negatives do not qualify a
genuine signed pair. The maintained local preview/Dev paired installer is filed
separately and remains unstarted until the coordinator schedules it. No owner
keychain or signing is accessed outside that maintained flow.

`select_own()` takes no path, PID, requirement, environment, configuration or
peer input. Security supplies the secured main-executable URL only after running
self validity succeeds. Exact `hgs`/`hgs-tray` paired layout, fixed identifier,
real files and a resource seal are required. Strict whole-app resource/nested
code and all-architecture validation, genuine Apple certificate signatures,
non-ad-hoc flags, nonempty CMS/certificates and matching derived teams precede
expectation selection. There is no literal Team ID. Stable designated
requirements are combined with the selected exact native code hashes.

The running self must satisfy the exact selected static generation; merely
copying its static code is insufficient. The SDK explicitly says that copying
static code from running code is not guaranteed to be secure. Metadata is
bounded and typed, embedded NUL refuses, and the whole fixed code/seal generation
is compared around validation. Fresh Security objects and running validity are
used for each revalidation, including before and after the original kernel-audit
peer observation. Missing, changed, mismatched, ambiguous, symlinked, bare or
ad-hoc selections refuse; source builds preserve their ordinary GUI behavior
because this module has no production caller.

These are synchronous Security/filesystem operations. A future host must run
them off UI and actor threads and retain its actual worker, connection and
admission past any timeout, cancellation or lost receiver. No timeout or
resource completion is inferred here. A successful observation is only valid at
the checked instant; it is neither an exec fence nor immutable installation or
upgrade authority. Concurrent installation/modification and complete runtime
resource/profile qualification remain gates before an actual host caller.
OS launch origin, manual frontend readiness, Notification Center/display and
owner acceptance are separate qualifications requiring an owner-given window.
